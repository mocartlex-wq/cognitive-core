# Доставка памяти и последнее состояние задачи

Обычный вопрос ищет слова с русской морфологией в исходных L1-записях. Если совпала старая контрольная точка, возвращается последнее сообщение **той же задачи**, включая повторное открытие после «готово». Проекты и агенты не сводятся в одну общую последнюю запись. L3 остаётся общим опытом, а статус — датированным сообщением автора, не доказательством текущей работы сервиса.

Миграция `0026` создаёт два GIN-индекса выражений (`russian` и `simple`) через `CONCURRENTLY`; данные не переписываются. Она умеет повторить прерванную сборку невалидного индекса. Поиск сначала отбирает совпадения по индексам, затем сравнивает слова и выбирает текущую точку задачи. Не включайте клиентов до успешного завершения миграции.

Необязательный аргумент `workspace` предпочитает точки указанной папки. `SessionStart` использует его с пустым запросом: новые явные точки могут вообще не содержать слова `CHECKPOINT`, имени домена или ветки в тексте.

`frame.recent` сохраняет совместимость. `frame.current` выделяет контрольные точки, `task_state_found` сообщает об их наличии. `state_warning` означает сбой поиска статусов, а не отсутствие задачи. Превью ограничено 1200 символами на поле и имеет `truncated=true`. Вызов `cognitive_read_record(record_id=...)` возвращает полный источник, автора, дату, `is_latest` и `superseded_by`. Полное тело находится в `content`, метаданные контрольной точки — в `checkpoint`, без второй копии исходного текста. Обычные заметки ищутся за последние семь дней, контрольные точки — без этого ограничения. Не следует делать вывод о готовности из текстового совпадения или старого L3-резюме.

## Явное состояние

`cognitive_remember` принимает прежние аргументы и два дополнительных: `idempotency_key` и `checkpoint`. Для состояния задачи используйте:

```json
{
  "domain": "cognitive_core",
  "task": "Восстановление памяти после перезапуска",
  "result": "Что проверено и где полное подтверждение",
  "idempotency_key": "one-stable-delivery-id",
  "checkpoint": {
    "schema_version": 1,
    "task_id": "memory-reliability",
    "session_id": "producer-session-id",
    "status": "awaiting_review",
    "next_step": "Проверить приёмку другим агентом",
    "evidence": ["ссылка на отчёт или проверяемый артефакт"],
    "workspace": "папка или URI проекта",
    "observed_at": "2026-11-15T09:00:00Z",
    "supersedes": null
  }
}
```

Для следующей точки той же задачи `supersedes` должен совпадать с ID текущей. При конфликте HTTP 409 сначала прочитайте новое состояние и согласуйте изменения. Не заменяйте автоматически чужую точку. `completed` требует непустой ссылки на подтверждение, но сервер не утверждает, что содержание ссылки проверено. Старые записи `CHECKPOINT domain [branch@sha]` группируются по ветке и явно помечаются `inferred_legacy_branch`; их статус `unknown`, текст сохраняется. Эта совместимость не заменяет явный `task_id` для нескольких задач в одной ветке.

Повторная доставка того же ключа тем же агентом, владельцем и доменом возвращает прежний ID. Другой текст под тем же ключом отклоняется. Потерянный HTTP-ответ не создаёт вторую запись. Ошибки REST в native MCP возвращают `isError=true`.

## Клиенты Codex и Claude Code

`tools/memory_hook.py` использует стандартный stdin JSON lifecycle hooks. `Stop` сохраняет полный `last_assistant_message` как **session_note**. Успешная запись ответа не превращается в `completed`. `PostToolUse` сохраняет изменённый Markdown из `.claude/.../memory/` целиком вместе с SHA256 и путём. Файл больше 200 KB вызывает явную ошибку, не обрезается. Домен берётся из явной карты `cwd`, не из сжатого имени каталога Claude. `SessionStart` читает последние точки и сообщает о недоставленной очереди. Несколько направлений сохраняются раздельно.

До HTTP данные фиксируются в локальном SQLite WAL с synchronous=FULL. Повторная отправка безопасна после завершения процесса. Очереди разделены по серверу и ключу; секрет в базе не хранится. При смене ключа старая очередь не пересылается новому аккаунту автоматически — требуется сверка принадлежности. HTTP 4xx (кроме 408/429) помечается как требующий проверки; сетевые сбои и 5xx повторяются с задержкой до пяти минут. Автоматического удаления исходников и очереди нет.

Runtime-конфигурация хранится вне Git, без ключей:

```json
{
  "endpoint": "https://mcp.example.org",
  "state_dir": "C:/Users/Owner/AppData/Local/cogcore/memory-v1",
  "agents": {
    "codex-desktop": {"credential_format": "codex_toml", "credential_file": "C:/Users/Owner/.codex/config.toml"},
    "claude-code": {"credential_format": "claude_json", "credential_file": "C:/Users/Owner/.claude.json"}
  },
  "projects": [
    {"path": "D:/work/core", "domain": "cognitive_core", "label": "Общая память"},
    {"path": "D:/work/crm", "domain": "ai_crm", "label": "CRM"}
  ]
}
```

Сначала выпустите сервер через обычный PR. Затем запустите `install_memory_hooks.py` с `--config`, стабильными `--python` (3.11+) и `--destination`. Без `--apply` он только печатает план. При `--apply` проверяет наличие новых MCP-возможностей **до** изменения файлов, сохраняет резервные копии, добавляет глобальные hooks и сохраняет квитанцию. Через повторяемый `--legacy-settings` укажите проектные settings с прежними memory hooks: удалятся только известные команды памяти, остальные hooks и разрешения сохранятся. `notify` в Codex не меняется. Установщик предназначен для Windows, где проверены команды оболочки.

**Codex требует доверия к новым hook definitions:** владелец открывает Settings → Hooks → Review. Скрипт не пишет хеши доверия и не использует обход проверки. Claude Code подхватит настройки в новой сессии. Это надо проверить реальным запуском после установки, а не считать исполнение Python-функции доказательством lifecycle интеграции.

Для повторов при отсутствии активной сессии запустите `tools/install_memory_retry.ps1 -Python <pythonw.exe> -Script <stable/memory_flush.py> -Config <runtime.json>`. Задача текущего пользователя работает раз в две минуты, без повышенных прав и пароля; `pythonw.exe` не открывает консоль. Она отправляет только уже сохранённые данные, пишет `delivery-health.json`, ограничена двумя минутами и не запускается параллельно сама с собой. При выходе пользователя из Windows доставка возобновится при следующем входе. Для серверных агентов используйте тот же протокол и outbox с их собственной конфигурацией и штатным планировщиком, не копируйте ключи других клиентов.

## Приёмка и откат

Регрессии: `tests/test_memory_reliability_db.py` на отдельной PostgreSQL-схеме, `test_memory_outbox.py`, `test_memory_hook.py`, `test_memory_install.py`, существующие recall/MCP тесты. Фикстуры `tests/fixtures/memory_acceptance_*` предназначены только для отдельной базы `/qa` с `COGCORE_MEMORY_QA=1`; они используют вымышленные ключи и не включают production scheduler или внешнюю LLM. Сценарий: запись → обрыв сети → новый процесс → сохранение → потеря подтверждения → перезапуск API → повтор → независимый агент через native MCP задаёт обычный вопрос. Проверяются последнее состояние, следующий шаг, полный источник, изоляция владельцев и отсутствие подмены неизвестной задачи. Адрес `qa://` — тестовый указатель, не доступный внешний документ.

После релиза повторите вопросы о реальных задачах чтением production, запустите настоящие Stop/SessionStart обоих клиентов и сравните квитанции. Пока этого нет, локальные и стендовые результаты не подтверждают production-готовность.

Действующая серверная санитизация не обходится: некоторые фрагменты программного кода могут быть отклонены или экранированы. Отклонённая запись видна как `failed`, оригинал остаётся в локальной очереди. Поэтому `source_sha256` относится к локальному исходнику, а не обязательно к экранированному тексту на сервере.

Откат клиента: отключить только установленные memory hooks, восстановить соответствующие `.memory-backup-*` из квитанции, отключить задачу `Cognitive Core - Memory outbox`. Сохранить SQLite и её WAL/SHM для восстановления. Откат сервера — обычный revert PR; добавлены только индексы, старые payload остаются JSONB. До отката сервера отключите новый отправитель, иначе старый API отклонит новые поля.
